# Approval Engine

The platform does not accept a caller-supplied username or role as proof of identity. Service code must configure `verify_identity(credential)` to validate a credential and return a `VerifiedApprover(subject, frozenset(roles), is_human=True)` based on trusted identity claims, or return `None` to deny. Also configure `can_approve(verified_identity, role, scope)` to check that the asserted role is authorized for the stored review. `scope` includes the canonical project path, execution ID, gate and target. Targets include the G4 repository/PR/base ref, G5 repository from verified build provenance, G6 environment and G7 incident. For G1–G3, target is empty and the scope is the project and gate. No identity verifier or no scoped role check means no regular approval. Pass canonical author IDs from trusted metadata; no artifact author can approve their own review.

`approve(execution_id, gate, credential, decision, role=..., review_id=..., artifact_sha256=..., evidence_refs=[...], comment=...)` records `approved`, `rejected`, `blocked`, or `changes_requested` for the active review. Approval requires evidence references; any non-approving decision requires a reason and blocks the gate. A later decision from the same person replaces their earlier decision; a current veto blocks the gate. Evidence references are recorded, not independently validated by this core. G5 needs both `qa_lead` and `product_owner` from distinct people. Release approval G6 is not a substitute for either G5 decision.

The [example policy](../config-examples/gate-policy.yaml) can be used as `.ai-sdlc/approval-policy.yaml`. Projects can narrow eligible built-in roles where applicable. Each review snapshots the eligible roles when opened; editing YAML cannot remove a veto on an open review. `required: false`, `null`, unknown roles/gates and removal of either required G5 role are rejected.

**Exceptions are disabled by default.** An organization can supply a trusted `can_authorize_exception(verified_identity, scope)` that only permits waivable controls and authorized humans. Call `authorize_exception` with the active review ID and digest, reason, risk, mitigation, owner, evidence and timezone-aware expiry. The gate determines the scope: only that review's stage transition or protected action. There is at most one exception per review. It cannot waive G5's dual approval, override a recorded veto, transfer to a new review or pass after expiry. The decision and any authorization citing it stay in the audit store. Legal and non-waivable controls must not be allowed by the callback; do not derive it from project YAML.
