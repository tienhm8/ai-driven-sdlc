# Approval Engine

See the [Framework gate policy](../../framework/governance/human-review-gates/gate-policy.md) for gate roles, decision rules and exceptions, and [Architecture](../docs/architecture.md#adapter-responsibilities) for what integrations must verify.

Configure `verify_identity(credential)` to return `VerifiedApprover(subject, frozenset(roles), is_human=True)` from trusted claims, or `None` to deny. `can_approve(verified_identity, role, scope)` must authorize the role for the stored review. `scope` has the canonical project path, execution ID, gate and target. The target is empty for G1–G3; for G5 it is the repository from verified build provenance. For G4, G6 and G7 use the target shapes in [Workflow Engine](../workflow-engine/README.md#api-usage). Without both callbacks the engine refuses regular approval.

Call `approve(execution_id, gate, credential, decision, role=..., review_id=..., artifact_sha256=..., evidence_refs=[...], comment=...)` for the active review. Use `approved`, `rejected`, `blocked` or `changes_requested`. Supply evidence references for approval or a reason in `comment` for any other decision. The engine records references but does not independently verify their contents. G6 approval does not replace either of the decisions required at G5.

Use the [example policy](../config-examples/gate-policy.yaml) as a starting point for `.ai-sdlc/approval-policy.yaml`. Projects can narrow eligible built-in roles where applicable, but cannot disable mandatory gates or remove required G5 roles. The validator and runtime share the parser; defaults apply when `.ai-sdlc` is absent or is a real directory without a policy entry. When present, `.ai-sdlc` must be a real directory and `approval-policy.yaml` must be a readable, valid regular file. Neither may be a symlink, even if the target exists. Violations block validation and new reviews. An existing review keeps the roles it captured when opened, so editing YAML does not change its decisions.

**Exceptions are disabled by default.** To enable eligible exceptions, configure a trusted `can_authorize_exception(verified_identity, scope)` independently of project YAML. Call `authorize_exception` with the active review ID and digest, reason, risk, mitigation, owner, evidence and timezone-aware expiry. The engine accepts at most one exception per review and records it and any authorization that cites it in the audit store. Review the [exception rules](../../framework/governance/human-review-gates/gate-policy.md#ngoại-lệ) before enabling the callback.
