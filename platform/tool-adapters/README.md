# Tool adapters

The shared [Model Router](../model-router/README.md) selects the profile and minimum portable effort. A managed binding is a separate decision: resolve the project's tool/model request against an operator-approved registry. A binding never authorizes data egress, budget spend or repository actions.

## Read-only binding preview

Place a dedicated registry outside the Project Instance and registered checkouts. Save each approved tool as `<tool-id>/adapter.yaml`; `name` must match the tool ID and `enabled` must be `true`. Use the [disabled example](adapter-contract.example.yaml) for the shape; its capabilities, settings and evidence are synthetic, not approvals. Verify capability and native effort for the exact tool/model/configuration before enabling it, and keep evidence current. The registry is administrator-controlled; do not copy model IDs, commands or credentials from an untrusted task or branch.

- The project's `ai.tool_bindings.<tool>.<profile>` can select an approved model. Without an explicit binding, the primary route uses the registry's approved `default_model`. This is a concrete model ID; the transport must not silently substitute whatever model the tool currently defaults to.
- The registry model record declares approved profiles, capabilities, data-policy ID, evidence reference and the native effort map. If the project provides its own effort mapping, it must match the approved map. Unknown or inadequate bindings require manual selection; the runner does not hunt for a cheaper or less capable model.
- A `routine/low` route may use uncontrolled default effort only if approved by `allow_uncontrolled_routine_effort`; record the effective effort as unverified when it cannot be observed. This exception does not apply to high-risk routes or automatic retries/fallbacks.

Run `resolve-context.py --adapters-dir <registry>` with the normal task flags for an approved binding preview. A `bound-preview` is not evidence that a provider ran, that permission was granted, or that budget is available. Without the option, the resolver retains its declaration-only preview. See [context resolution](../docs/context-resolution.md).

## Managed call boundary

`ManagedModelRunner` accepts only explicitly injected trusted transports and policy callbacks. It re-resolves the scope and relevant G3 evidence, then checks operator authorization for the requested scope, permission to send the exact payload to the bound destination, and budget approval **before each attempt**. `authorize_scope`, `allow_data` and `allow_budget` must return `True` to proceed; no permissive defaults are supplied. Missing evidence, callback errors, or failed audit before dispatch block the call. Bind the budget decision to the Story, route and attempt in the callback. This is a preflight interface, not a reservation, usage ledger or hard USD cap (section 5).

An injected transport receives only the bound route and opaque inference bytes, not the work-item ID, checkout or governance metadata. It may issue **one** inference request per invocation; it must not perform tool actions, run its own retry/fallback, or reuse a mutable agent session. A future real integration must enforce these constraints and report provider-observed model/effort (not echo the request or trust model text). Scope authorization must come from authenticated operator-side policy and cover the exact action; no grant comes from an input role label. Merge and other repository mutations remain with the existing action boundary. Keep credentials and audit sinks outside the prompt and workspace.

Only classified temporary errors explicitly marked safe to repeat can trigger another attempt. Respect the reported delay; if the delay exceeds the local 120-second ceiling, stop for manual handling instead of sending early. The v1 policy permits at most one retry and one non-chained fallback. Fallback is selected from the shared policy and needs an explicit binding, the same data policy, a capability superset and at least the same effort. A refusal, missing input, denied permission, exhausted budget or uncertain outcome never triggers another route. The local audit callback gets route metadata (`requested_*`, `effective_*`, observation status, transition reason), not the prompt, output, payload digest or machine path. Mismatches and missing required observations stop the run for manual handling.

This release includes the binding and guarded runner, **not** a live provider transport. Offline tests inject two fixture transports. Projects can enable a single approved tool; a second tool and cross-tool fallback are not required. Live verification is separate and can be deferred to rollout. The fixtures are not capability evidence for real tools. See the [routing acceptance checklist](../docs/routing-acceptance.md).
