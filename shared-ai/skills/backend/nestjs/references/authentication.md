# Authentication, authorization, and data partition

Open when changing an auth guard, issuer, role, ownership check, or partition scope. Use the existing `authentication` or `authorization` skill when designing a change to the respective mechanism.

1. Follow a comparable endpoint. Inspect `src/common/guard/` and the owning modules under `src/modules/auth/`, `src/modules/sso/`, `src/modules/user/`, and `src/modules/data-partition/`. Reuse the approved JWT or Keycloak/JWKS guard and role metadata. Verify the trusted issuer and the endpoint's actual guard chain; do not treat a role, a frontend UI check, or a caller-provided resource ID as proof of access.
2. Keep identity and resource authorization separate. For HTTP, `DataPartitionGuard` uses route/controller metadata to determine whether partitioning is enabled and required. The `x-data-partition-code` header is a selection, not proof of membership. Where applicable, the guard checks membership against the authenticated subject and sets the validated partition and scope in CLS. Verify the route metadata, CLS values, and the active adapter's entity-specific `dpConfig` together; there is no global assumption that partitioning is enabled or required for every entity. Do not copy the User repository's partition setting or a special internal bypass into a new feature.
3. Apply authorized scope to list, count, lookup, and mutation queries when relevant. Preserve the existing error contract instead of revealing whether an inaccessible resource exists. HTTP guards and context are not automatically valid for RPC; use the [transport reference](microservice-transports.md) for a transport change.
4. Test one allowed path and relevant denial paths: missing or invalid identity, missing role, wrong resource/partition membership, and missing partition on required routes. Use `401` for failed authentication and the approved forbidden/not-found response for unauthorized resources. Where scope affects persistence, verify both returned rows or counts and that unauthorized writes leave data unchanged. Keep credentials, JWTs, and sensitive data out of fixtures and logs.
