# Microservice transports

Open for gRPC, custom TCP, or internal HTTP changes. The reference base boots one hybrid Nest 11.2.7 application with HTTP/Express, gRPC, and a custom observed TCP server (`src/main.ts`). That does not make each Nest module an independently deployed service. Add the `microservices` skill when changing service ownership, deployment boundaries, or a cross-service contract.

1. **Find both ends.** For gRPC, start in `src/modules/microservice/grpc/proto/` (server and client definitions), the gRPC client factory, and the registered handler. For TCP, follow the client token in `src/modules/microservice/tcp/tcp-client.provider.ts`, its send/emit call site, and the matching `@MessagePattern` or `@EventPattern` handler where applicable. For internal HTTP, read the named client in `src/modules/internal-http/` and the receiving route. Verify actual registration in `microservice.module.ts` and bootstrap; RabbitMQ configuration exists but is not wired into the inspected base. Bull/Redis queues are not the RPC transport.
2. **Preserve the contract.** Check payloads in both directions, validation, error semantics, and compatibility with older peers. For gRPC, do not renumber or reuse field tags; account for clients and servers that roll out separately. For TCP, preserve the compatibility behavior documented in `docs/tcp-context.md`; a raw-payload fallback for an old peer does not bypass authorization. Separate business payload from metadata and do not add credentials or user data to telemetry context.
3. **Verify the actual transport boundary.** Trace identity, partition and request context, guards, interceptors, and filters on that transport; do not assume the HTTP pipeline is inherited. Preserve timeout/cancellation and error semantics. Add retries only for operations where duplicate execution is safe or explicitly controlled; verify downstream failure behavior rather than silently retrying side effects.
4. **Test both ends as appropriate.** Use focused handler/client tests and an integration check when changing serialization, transport registration, auth/context propagation, or compatibility. For TCP context or serializer changes, use the existing tests under `src/modules/microservice/tcp/` and, in a suitable local environment, the smoke documented in `docs/tcp-context.md`: `npm run build` then `node test/tcp-context.smoke.cjs`. Check expected success, rejection, and timeout/downstream failure for the affected contract. Do not report an external peer or an end-to-end path as verified unless exercised.
